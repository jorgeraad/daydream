## 1. Overview

The multi-zone system enables Daydream's world to extend beyond a single screen. As the player explores, new zones generate lazily around them — each zone a tile map that connects seamlessly to its neighbors. This is the biggest architectural addition to the MVP: it spans all four packages (engine, AI, renderer, game) and introduces background generation, memory management, and transition choreography.

The system turns a single-room demo into an infinite, explorable world.

### What This Document Covers

- **Zone graph model**: How zones relate to each other spatially
- **Lazy generation pipeline**: When and how new zones are created via AI
- **Preloading strategy**: Background generation to eliminate wait times
- **Memory management**: Loading/unloading zones to stay within budget
- **Zone transitions**: Visual effects when the player crosses zone boundaries
- **Edge coherence**: Ensuring terrain connects naturally between adjacent zones

---

## 2. Goals & Non-Goals

### Goals

- Player can walk in any direction and encounter newly generated zones
- Zone transitions feel smooth (< 500ms perceived latency in the common case)
- Adjacent zones have visually coherent terrain at boundaries (rivers connect, paths continue)
- Memory stays bounded regardless of how many zones the player has explored
- Previously visited zones reload from SQLite without re-generation
- Architecture supports future evolution to seamless cross-zone scrolling

### Non-Goals

- **Seamless scrolling** (rendering multiple zones simultaneously) — deferred to a future iteration, but the design must not preclude it
- **Non-grid zone layouts** (portals, warps, irregular connections) — coordinate-based grid only for now
- **Building interiors** (entering a building loads an interior zone) — Phase 3 feature
- **Multiplayer zone sharing** — out of scope
- **Zone editing** (player modifying terrain) — out of scope

## 4. Configuration

All tunable parameters are centralized in a single config object. Sensible defaults are provided — changing behavior should be as simple as changing a number.

```typescript
// packages/engine/src/world/zone-config.ts

export interface ZoneConfig {
  /** Width of each zone in tiles. Default: 80 */
  zoneWidth: number
  /** Height of each zone in tiles. Default: 40 */
  zoneHeight: number
  /** Manhattan distance — zones within this radius stay in memory. Default: 2 */
  keepRadius: number
  /** Maximum concurrent AI generation calls. Default: 4 */
  maxConcurrentGenerations: number
  /** Number of tile rows/columns to blend at zone boundaries. Default: 3 */
  edgeBlendDepth: number
  /** Fade-out duration in ms during zone transition. Default: 300 */
  transitionFadeOutMs: number
  /** Fade-in duration in ms during zone transition. Default: 200 */
  transitionFadeInMs: number
}

export const DEFAULT_ZONE_CONFIG: ZoneConfig = {
  zoneWidth: 80,
  zoneHeight: 40,
  keepRadius: 2,
  maxConcurrentGenerations: 4,
  edgeBlendDepth: 3,
  transitionFadeOutMs: 300,
  transitionFadeInMs: 200,
}
```

All components (`ZoneManager`, `ZoneBuilder`, `TransitionManager`, `EdgeCoherence`) receive relevant values from this config rather than using hardcoded numbers. The config is created once at game startup and threaded through — no global state.

## 5. Architecture

### 5.1 Zone Graph Model

The world is an implicit infinite grid. Zones are identified by their `(x, y)` coordinate, encoded as `"zone_X_Y"`. Adjacency is computed from coordinates — no explicit graph edges needed.

```
         zone_0_-1
              |
zone_-1_0 — zone_0_0 — zone_1_0
              |
         zone_0_1
```

The player starts at `zone_0_0`. Zones extend infinitely in all directions. Only explored zones exist in storage; unexplored coordinates are empty until generated.

### 5.2 Zone Lifecycle

A zone progresses through these states:

```
unknown → generating → loaded → active → loaded → unloaded
                                  ↑                    |
                                  |    (reload from    |
                                  +---- SQLite) -------+
```

| State | In Memory | In SQLite | Description |
|-------|-----------|-----------|-------------|
| **unknown** | No | No | Never visited or generated. Coordinates exist implicitly. |
| **generating** | No (Promise pending) | No | AI generation in progress. A Promise resolves to the zone. |
| **loaded** | Yes | Yes | In memory and persisted. Adjacent to active zone. |
| **active** | Yes | Yes | Currently rendered in the viewport. Player is here. |
| **unloaded** | No | Yes | Too far from player. Persisted but removed from memory. |

### 5.3 ZoneManager

The new `ZoneManager` class is the central orchestrator for multi-zone operations. It lives in `@daydream/engine` and manages the zone lifecycle without depending on AI or rendering.

```typescript
class ZoneManager {
  private zones: Map<ZoneId, Zone>                    // In-memory zones
  private generating: Map<ZoneId, Promise<Zone>>      // In-flight generations
  private activeZoneId: ZoneId

  // --- Core Operations ---

  // Get a zone, loading from storage if needed
  getZone(id: ZoneId): Zone | undefined

  // Get the currently active zone
  getActiveZone(): Zone

  // Set the active zone (triggers preloading + unloading)
  async activateZone(id: ZoneId): Promise<void>

  // --- Generation ---

  // Request generation of a zone (returns existing if already loaded/generating)
  async ensureZone(id: ZoneId): Promise<Zone>

  // Check if a zone is ready (loaded or active)
  isReady(id: ZoneId): boolean

  // Check if a zone is being generated
  isGenerating(id: ZoneId): boolean

  // --- Preloading ---

  // Preload adjacent zones (called after zone activation)
  preloadAdjacent(center: ZoneId, movementDirection?: Direction): void

  // --- Memory ---

  // Unload zones beyond the keep radius
  unloadDistant(activeCoords: Point, keepRadius: number): ZoneId[]

  // --- Edge Coherence ---

  // Get edge tile data for coherence when generating adjacent zones
  getEdgeData(id: ZoneId, edge: Direction): EdgeSignature | undefined
}
```

ZoneManager delegates actual generation to a **`ZoneGenerator`** callback (injected at construction). This keeps the engine package free of AI dependencies:

```typescript
type ZoneGeneratorFn = (
  id: ZoneId,
  coords: Point,
  context: ZoneGenerationContext,
) => Promise<Zone>

interface ZoneGenerationContext {
  worldSeed: WorldSeed
  adjacentZones: Map<Direction, { metadata: ZoneMetadata; edgeData: EdgeSignature }>
  chronicle: { recentSummary: string; activeThreads: string[] }
}
```

The game package provides the concrete implementation that calls AIClient.

### 5.4 Interaction Between Components

```
GameShell (orchestrator)
  │
  ├── ZoneManager (engine) ← zone lifecycle, preloading, memory
  │     ├── ZoneGenerator callback ← AI generation (provided by game)
  │     └── ZoneStore callback ← SQLite load/save (provided by game)
  │
  ├── TransitionManager (renderer) ← fade animations
  │
  ├── ViewportManager (renderer) ← camera tracking
  │
  └── TileRenderer (renderer) ← draws tiles to FrameBuffer
```

When the player moves to a zone edge:

```
1. GameShell detects edge collision
2. GameShell asks ZoneManager: is the adjacent zone ready?
   a. Yes → proceed to transition
   b. No → show loading gate, await zone
3. GameShell tells TransitionManager: start fade-out
4. GameShell tells ZoneManager: activateZone(adjacentId)
   - ZoneManager swaps activeZoneId
   - ZoneManager kicks off preloadAdjacent() for new neighbors
   - ZoneManager runs unloadDistant()
5. GameShell updates player position to opposite edge
6. GameShell tells ViewportManager: reset camera for new zone
7. GameShell tells TransitionManager: start fade-in
8. GameShell tells TileRenderer: render new zone
```

## 6. Lazy Generation Pipeline

### 6.1 Generation Trigger

Zone generation is triggered in two scenarios:

1. **Preloading**: When the player enters a zone, ZoneManager preloads all 4 cardinal neighbors. This is the primary path — most zones are generated before the player arrives.

2. **On-demand**: If the player reaches an edge before preloading completes (e.g., they moved very quickly or generation was slow), the transition blocks behind a loading gate until generation finishes.

### 6.2 Generation Flow

```
ZoneManager.ensureZone(id)
  │
  ├── Check in-memory cache (zones Map) → return if found
  ├── Check in-flight generations (generating Map) → return Promise if found
  ├── Check SQLite (via ZoneStore callback) → load, cache, return if found
  │
  └── Start new generation:
      │
      ├── Compute coords from zone ID
      ├── Determine biome (from WorldSeed biome distribution + noise)
      ├── Gather context:
      │   ├── World seed (setting, rules, tone)
      │   ├── Adjacent zone metadata + edge data (for coherence)
      │   ├── Chronicle summary + active narrative threads
      │   └── Biome palette for these coordinates
      │
      ├── Call ZoneGenerator callback (→ AIClient + ZoneBuilder)
      │   ├── AI generates ZoneSpec (terrain, buildings, characters, narrative)
      │   ├── ZoneBuilder converts spec → tile data
      │   └── Edge blender post-processes boundary tiles
      │
      ├── Store result in SQLite
      ├── Add to in-memory cache
      └── Return zone
```

### 6.3 Deduplication

The `generating` Map ensures that if multiple paths request the same zone simultaneously (e.g., preloading + player movement), only one generation runs. All callers receive the same Promise.

```typescript
async ensureZone(id: ZoneId): Promise<Zone> {
  // Already loaded
  const existing = this.zones.get(id)
  if (existing) return existing

  // Already generating
  const pending = this.generating.get(id)
  if (pending) return pending

  // Try SQLite
  const stored = await this.zoneStore.load(id)
  if (stored) {
    this.zones.set(id, stored)
    return stored
  }

  // Generate
  const promise = this.generateZone(id)
  this.generating.set(id, promise)
  promise.then(zone => {
    this.zones.set(id, zone)
    this.generating.delete(id)
  }).catch(() => {
    this.generating.delete(id)
  })
  return promise
}
```

## 7. Preloading Strategy

### 7.1 When to Preload

Preloading is triggered every time the active zone changes (via `ZoneManager.activateZone()`). On activation, ZoneManager identifies the 4 cardinal neighbors and calls `ensureZone()` for each.

### 7.2 Priority Order

When the player transitions with a known movement direction, adjacent zones are generated in priority order:

1. **Movement direction** — the zone ahead of the player (highest chance of being needed next)
2. **Perpendicular directions** — the two zones to the sides
3. **Opposite direction** — the zone behind the player (lowest priority, player just came from there and it's likely already loaded)

```typescript
function preloadOrder(direction: Direction): Direction[] {
  switch (direction) {
    case "up":    return ["up", "left", "right", "down"]
    case "down":  return ["down", "left", "right", "up"]
    case "left":  return ["left", "up", "down", "right"]
    case "right": return ["right", "up", "down", "left"]
  }
}
```

If no movement direction is known (e.g., game load, teleport), all 4 are generated with equal priority.

### 7.3 Concurrency

Up to **4 concurrent AI calls** for zone generation. Since each preload cycle requests exactly 4 zones, and many will already be loaded (the zone the player came from, previously visited neighbors), the actual number of simultaneous AI calls is typically 1-3.

```typescript
// Concurrency is naturally bounded:
// - ensureZone() deduplicates (no double-generation)
// - Already-loaded zones return immediately
// - At most 4 zones requested per activation
```

If rate limiting becomes an issue, a semaphore can be added to ZoneManager to cap concurrent AI calls. This is not expected for MVP (4 concurrent Sonnet calls is well within typical rate limits).

### 7.4 No Cancellation

Pending generations are **not** cancelled when the player moves to a different zone. Reasons:

- Generated zones are cached in SQLite — the work is never wasted
- Cancelling mid-generation is complex (AI calls aren't easily cancellable)
- The player may return to the area later
- Generation completes in 2-4s, which is short enough to not be wasteful

## 8. Memory Management

### 8.1 In-Memory Budget

Keep zones within **Manhattan distance ≤ 2** from the active zone. This means:

- Distance 0: active zone (1 zone)
- Distance 1: cardinal neighbors (up to 4 zones)
- Distance 2: two-hop neighbors (up to 8 zones)
- **Maximum: 13 zones in memory**

In practice, fewer will be loaded because not all zones in the radius will have been explored yet.

```
        ·  2  ·
     2  1  1  1  2
  ·  1  0  1  ·
     2  1  1  1  2
        ·  2  ·

  0 = active    (1 zone)
  1 = distance 1 (4 zones)
  2 = distance 2 (8 zones)
  · = not loaded (diagonal gaps)
```

The actual footprint for a ring-2 neighborhood using Manhattan distance:

```
      2
    2 1 2
  2 1 0 1 2
    2 1 2
      2
```

That's 1 + 4 + 8 = 13 zones maximum.

### 8.2 Memory Per Zone

Rough estimate per zone (default 80×40 tiles, scales with `zoneWidth` × `zoneHeight`):

| Data | Size |
|------|------|
| Ground layer (3200 TileCells × ~50 bytes each) | ~160 KB |
| Objects layer | ~160 KB |
| Collision layer (binary) | ~3 KB |
| Buildings, objects, metadata | ~5 KB |
| Characters (references only) | ~1 KB |
| **Total per zone** | **~330 KB** |

At 13 zones maximum: **~4.3 MB**. Well within the 100 MB budget.

### 8.3 Unload Policy

When the player transitions to a new zone, `unloadDistant()` runs:

1. Compute Manhattan distance from the new active zone to every loaded zone
2. Any zone with distance > 2 is a candidate for unloading
3. For each candidate:
   a. If dirty (modified since last save), persist to SQLite first
   b. Remove from the in-memory `zones` Map
   c. Remove any characters exclusive to that zone from the character registry

```typescript
unloadDistant(activeCoords: Point, keepRadius: number = 2): ZoneId[] {
  const unloaded: ZoneId[] = []
  for (const [id, zone] of this.zones) {
    const distance = Math.abs(zone.coords.x - activeCoords.x)
                   + Math.abs(zone.coords.y - activeCoords.y)
    if (distance > keepRadius) {
      this.zoneStore.saveIfDirty(zone)
      this.zones.delete(id)
      unloaded.push(id)
    }
  }
  return unloaded
}
```

### 8.4 Character Handling on Unload

Characters exist in the WorldState character registry (`Map<CharacterId, Character>`). When a zone is unloaded:

- Characters whose `state.currentZone` matches the unloaded zone are **also unloaded** from the in-memory registry (but remain in SQLite)
- Characters that have moved to a still-loaded zone are kept
- On zone reload, characters are rehydrated from SQLite

This is simple because characters track their current zone via `state.currentZone`.

## 9. Zone Transitions

### 9.1 Discrete Transition Flow

The MVP uses discrete transitions (full zone swap with a fade animation). The player reaches the zone edge, the screen fades out, the zone swaps, and it fades back in.

**Step-by-step:**

```
1. Player presses movement key toward zone edge
2. GameShell detects: next position is out of bounds
   (e.g., playerX would become -1, or playerX would become zoneWidth)
3. Compute adjacent zone ID from current zone coords + direction
4. Check ZoneManager.isReady(adjacentId)
   │
   ├── Ready:
   │   a. Start fade-out animation (300ms)
   │   b. ZoneManager.activateZone(adjacentId)
   │   c. Compute new player position (opposite edge):
   │      - Moving left:  newX = zone.width - 1, newY = playerY
   │      - Moving right: newX = 0, newY = playerY
   │      - Moving up:    newX = playerX, newY = zone.height - 1
   │      - Moving down:  newX = playerX, newY = 0
   │   d. Update WorldState: player.position, activeZoneId
   │   e. Reset ViewportManager camera for new zone
   │   f. Render new zone (hidden behind fade)
   │   g. Start fade-in animation (200ms)
   │
   └── Not ready:
       a. Show loading gate (see §9.3)
       b. Await ZoneManager.ensureZone(adjacentId)
       c. Then proceed with fade transition above
```

### 9.2 Transition Animation

The fade effect uses color dimming — all tile foreground/background colors are interpolated toward black over 300ms, then interpolated back from black over 200ms.

```typescript
class TransitionManager {
  private renderer: CliRenderer
  private transitioning: boolean = false

  async fadeTransition(
    onSwap: () => void,   // Called at the midpoint to swap zone data
    fadeOutMs: number = 300,
    fadeInMs: number = 200,
  ): Promise<void> {
    this.transitioning = true

    // Phase 1: Fade out (dim toward black)
    await this.animateDim(1.0, 0.0, fadeOutMs)

    // Phase 2: Swap zone data (instant, happens while screen is black)
    onSwap()

    // Phase 3: Fade in (brighten from black)
    await this.animateDim(0.0, 1.0, fadeInMs)

    this.transitioning = false
  }

  // Returns true if a transition is in progress (block input)
  get isTransitioning(): boolean { return this.transitioning }
}
```

During the fade, player input is blocked to prevent movement during the transition.

Implementation detail: The dim effect can be achieved by applying a brightness multiplier to the FrameBuffer's colors before rendering. OpenTUI's `requestLive()` enables continuous rendering during the animation.

### 9.3 Loading Gate Fallback

If the adjacent zone isn't ready when the player reaches the edge, a loading gate appears:

1. Player's movement is blocked at the edge (they can still move in other directions)
2. A subtle visual indicator appears at the boundary — a row/column of dimmed cells or a pulsing `░` pattern
3. When the zone becomes ready, the indicator clears and the player can cross

The loading gate is **not** a full-screen loading screen. It's a localized effect at the zone boundary that the player walks through once it clears.

```typescript
class LoadingGate {
  private active: boolean = false
  private edge: Direction
  private zone: ZoneData

  show(edge: Direction, zone: ZoneData): void {
    this.active = true
    this.edge = edge
    this.zone = zone
    // Render pulsing ░ characters along the zone edge
  }

  hide(): void {
    this.active = false
    // Restore original edge tiles
  }

  // Called each frame to animate the gate
  update(deltaMs: number): void {
    if (!this.active) return
    // Pulse the gate tiles between ░ and ▒
  }
}
```

### 9.4 Future Path: Seamless Scrolling

The discrete transition system is designed to be replaceable with seamless scrolling without restructuring the core architecture. Key design decisions that enable this:

**1. World-coordinate player position**

The player's position is stored in world coordinates, not zone-local coordinates:

```typescript
// World coordinates = zone offset + local position
worldX = zone.coords.x * ZONE_WIDTH + localX
worldY = zone.coords.y * ZONE_HEIGHT + localY
```

For the discrete MVP, GameShell converts between world and local coordinates at transition boundaries. For seamless scrolling, the player always moves in world coordinates and the renderer resolves which zone's tiles to draw.

**2. TileSource abstraction**

The TileRenderer can be refactored to accept a `TileSource` interface instead of a single zone:

```typescript
// Future interface — not implemented in MVP
interface TileSource {
  getTileAt(worldX: number, worldY: number, layer: TileLayerName): TileCell | null
  isPassable(worldX: number, worldY: number): boolean
}

// MVP: wraps a single zone
class SingleZoneTileSource implements TileSource { ... }

// Future: composites multiple loaded zones
class MultiZoneTileSource implements TileSource {
  getTileAt(worldX: number, worldY: number, layer: TileLayerName): TileCell | null {
    const zoneX = Math.floor(worldX / ZONE_WIDTH)
    const zoneY = Math.floor(worldY / ZONE_HEIGHT)
    const zone = this.zoneManager.getZone(zoneId(zoneX, zoneY))
    if (!zone) return null
    const localX = worldX - zoneX * ZONE_WIDTH
    const localY = worldY - zoneY * ZONE_HEIGHT
    return getTileAt(getLayer(zone, layer)!, localX, localY)
  }
}
```

**3. ViewportManager in world coordinates**

The viewport camera can track world coordinates instead of zone-local coordinates. For the discrete MVP, the camera resets on each transition. For seamless scrolling, it tracks continuously.

These abstractions are **not** built for the MVP. They're documented here to ensure the MVP design doesn't create obstacles. The migration path:

1. Add `TileSource` interface
2. Refactor `TileRenderer.renderZone()` to use `TileSource.getTileAt()` instead of direct zone access
3. Switch `ViewportManager` to world coordinates
4. Replace `TransitionManager.fadeTransition()` with continuous scrolling
5. Adjust zone activation to be camera-position-driven rather than edge-triggered

## 10. Edge Coherence System

Zone boundaries should feel natural. A river flowing east out of one zone should continue into the next zone. A path leading north should connect to something in the zone above.

The system uses a **layered approach**: the AI generates with narrative awareness of neighbors, then the ZoneBuilder post-processes edges to guarantee visual continuity.

### 10.1 Layer 1: AI Narrative Hints

When generating a new zone, the AI receives descriptions of adjacent zones that already exist:

```typescript
// Included in the zone generation prompt context
interface AdjacentZoneHint {
  direction: Direction
  name: string
  description: string
  biome: string
  // Key features at the shared boundary
  edgeFeatures: string[]  // e.g., ["river flowing east", "stone path", "forest edge"]
}
```

The zone generation prompt includes these hints:

```
Adjacent zones:
- NORTH: "The Market Square" (village biome) — southern edge has a cobblestone road
  leading south and a small pond in the southeast corner.
- EAST: (unexplored — forest biome expected based on world seed)
- SOUTH: (unexplored)
- WEST: "The Old Bridge" (forest biome) — eastern edge has a river and a wooden
  bridge crossing it.
```

This gives the AI enough context to generate coherent zones. The AI should naturally place the road continuation and river entrance.

### 10.2 Layer 2: ZoneBuilder Edge Blending

After the AI generates the zone spec and ZoneBuilder converts it to tile data, a post-processing pass blends the edges:

**Edge Signature**: A compact representation of what's at a zone boundary.

```typescript
interface EdgeSignature {
  direction: Direction
  tiles: EdgeTile[]  // One per cell along the shared boundary
}

interface EdgeTile {
  position: number       // Index along the edge (0 to width-1 or height-1)
  terrain: string        // "ground" | "water" | "path" | "wall" | "building"
  char: string           // The tile character
  fg: string             // Foreground color
  bg?: string            // Background color
}
```

**Extraction**: When a zone is generated, edge signatures are extracted for all 4 edges and cached. These are stored alongside the zone (in metadata or a dedicated field).

```typescript
function extractEdgeSignature(zone: Zone, edge: Direction): EdgeSignature {
  const groundLayer = getLayer(zone, "ground")!
  const tiles: EdgeTile[] = []

  // For north edge: row 0, iterate columns
  // For south edge: row height-1, iterate columns
  // For west edge: column 0, iterate rows
  // For east edge: column width-1, iterate rows

  const isHorizontal = edge === "north" || edge === "south"
  const length = isHorizontal ? groundLayer.width : groundLayer.height

  for (let i = 0; i < length; i++) {
    const x = isHorizontal ? i : (edge === "west" ? 0 : groundLayer.width - 1)
    const y = isHorizontal ? (edge === "north" ? 0 : groundLayer.height - 1) : i
    const tile = getTileAt(groundLayer, x, y)
    if (tile) {
      tiles.push({
        position: i,
        terrain: classifyTerrain(tile),  // infer from char/color
        char: tile.char,
        fg: tile.fg,
        bg: tile.bg,
      })
    }
  }

  return { direction: edge, tiles }
}
```

**Blending**: After ZoneBuilder produces the new zone's tiles, the edge blender checks adjacent zones' edge signatures and adjusts the new zone's boundary tiles:

```typescript
function blendEdge(
  newZone: Zone,
  neighborEdge: EdgeSignature,
  blendDirection: Direction,
  blendDepth: number = DEFAULT_ZONE_CONFIG.edgeBlendDepth,
): void {
  for (const neighborTile of neighborEdge.tiles) {
    const pos = neighborTile.position

    // If neighbor has water at the boundary and new zone doesn't,
    // extend water into the new zone for blendDepth cells
    if (neighborTile.terrain === "water") {
      extendTerrain(newZone, blendDirection, pos, "water", blendDepth)
    }

    // If neighbor has a path at the boundary,
    // ensure the new zone has a path connection
    if (neighborTile.terrain === "path") {
      extendTerrain(newZone, blendDirection, pos, "path", blendDepth)
    }
  }
}
```

The blend depth (configurable via `ZoneConfig.edgeBlendDepth`, default 3) creates a smooth transition zone where terrain from the neighbor "leaks" into the new zone, avoiding hard cuts.

### 10.3 Coherence Guarantees

| Terrain Type | Coherence Approach |
|-------------|-------------------|
| **Water** (rivers, ponds) | Hard constraint: if neighbor has water at edge, new zone must have water at the matching position. Blend extends water `edgeBlendDepth` cells in. |
| **Paths** (roads, trails) | Hard constraint: path at neighbor edge → path continues into new zone. ZoneBuilder ensures path connects to something (building, zone center, or another edge). |
| **Ground** (grass, sand, stone) | Soft blend: new zone's edge cells use the neighbor's ground palette for a gradual biome transition if biomes differ. |
| **Buildings** | No blending. Buildings don't span zone boundaries. If a building is at a zone edge, the neighboring zone may have a complementary structure (e.g., a fence, garden, or road leading to it), handled by AI narrative hints. |

## 13. Performance Budget

| Operation | Target | Strategy |
|-----------|--------|----------|
| **Zone generation (AI call)** | 2-4s | Background preloading. Player rarely waits. |
| **Zone load from SQLite** | < 50ms | JSON parse + hydration. Already fast with bun:sqlite. |
| **Zone transition (visual)** | 500ms total | 300ms fade-out + 200ms fade-in. Zone swap is instant. |
| **Edge blending** | < 10ms | Pure tile manipulation, no AI call. |
| **Memory per zone** | ~330 KB | Tile arrays dominate. 13 zones = ~4.3 MB. |
| **Max memory (zones)** | ~5 MB | Well within 100 MB budget. Leaves room for other state. |
| **Concurrent AI calls** | 4 max | Rate-limit safe for Sonnet tier. |
| **Preload cycle** | < 5s total | 4 parallel calls. Most zones already cached. |
| **Unload cycle** | < 5ms | Map iteration + deletion. Save-if-dirty is async. |

### Worst Case: Player Sprint

If the player moves rapidly through zones (crossing a zone every few seconds):

- Each transition triggers 4 preload requests
- Most will hit the in-memory cache or SQLite (already generated)
- At most 1-2 new zones need AI generation per transition
- The loading gate catches the rare case where the player outruns generation

With default 80×40 tile zones (`zoneWidth` × `zoneHeight`) and player movement of 1 tile per keypress, crossing a zone takes at minimum ~40 keypresses. At a fast typing speed of 5 keys/second, that's 8 seconds per zone — enough time for AI generation to complete.

## 15. Appendices

### Appendix A: Discrete vs. Seamless Transitions

**Decision**: Discrete transitions for MVP, with architecture that enables future seamless scrolling.

**Options considered**:

1. **Discrete (chosen)**: Player reaches edge → fade → zone swap → fade in. Single zone rendered at a time.
   - Pros: Simple, matches existing ViewportManager, traditional roguelike feel, predictable performance
   - Cons: Brief interruption when crossing zones

2. **Seamless scrolling**: Render tiles from multiple zones simultaneously, camera scrolls continuously across boundaries.
   - Pros: More immersive, no visible transitions
   - Cons: Significantly more complex (multi-zone tile composition, world-coordinate camera, edge cases at corners), higher rendering cost

**Rationale**: Discrete transitions are the right starting point. They're simpler to implement and debug, and they establish the zone lifecycle infrastructure that seamless scrolling would also need. The key abstractions (TileSource, world coordinates) are documented as the migration path.

### Appendix B: Edge Coherence — Layered Approach

**Decision**: Use both AI narrative hints (soft) and ZoneBuilder post-processing (hard) for edge coherence.

**Options considered**:

1. **AI-only (narrative hints)**: Pass adjacent zone descriptions to the AI, let it make coherent choices.
   - Pros: Simplest implementation, natural-feeling results
   - Cons: AI may occasionally miss edge alignment (river exits at column 15, but AI places the continuation at column 20)

2. **Constraint-based (edge signatures only)**: Extract exact tile data at boundaries, force the new zone to match.
   - Pros: Pixel-perfect alignment guaranteed
   - Cons: Over-constrained, may produce awkward zone layouts that feel forced

3. **Both / layered (chosen)**: AI generates with narrative awareness, then ZoneBuilder post-processes edges.
   - Pros: Natural layouts from AI + guaranteed visual continuity from post-processing
   - Cons: More complex pipeline, possible tension between AI intent and blender output

**Rationale**: The layered approach gives us the best of both worlds. The AI makes creative decisions informed by neighbor context (ensuring narrative coherence), and the blender handles the mechanical alignment (ensuring visual continuity). The blender operates on a configurable border depth (`edgeBlendDepth`, default 3 cells), so it only adjusts the very edge of the zone — the AI's creative choices dominate the zone's interior.

### Appendix C: Loading Gate Fallback

**Decision**: Show a localized loading indicator at the zone boundary when the adjacent zone isn't ready.

**Options considered**:

1. **Block movement**: Player can't step past the edge. Invisible wall.
   - Pros: Simplest, no UI needed
   - Cons: Confusing — player doesn't know why they can't move

2. **Loading gate (chosen)**: Visual indicator at the boundary, player waits.
   - Pros: Honest about what's happening, player can do other things (explore current zone, talk to characters)
   - Cons: Needs a visual effect to communicate the state

3. **Queue + animate**: Player walks into edge and a long fade plays while generation completes.
   - Pros: Smoothest experience
   - Cons: Fade duration is unpredictable (depends on AI latency), could be awkwardly long

**Rationale**: The loading gate is the most honest and flexible approach. The player sees that something is generating and can choose to wait or explore elsewhere. It avoids the awkward variable-length fade of option 3 and the confusion of option 1.

### Appendix D: Concurrency Limit

**Decision**: Up to 4 concurrent zone generation AI calls.

**Rationale**: Each preload cycle requests at most 4 zones (cardinal neighbors). In practice, most will already be loaded, so the actual concurrent AI calls are typically 1-3. Four concurrent Sonnet calls are well within Anthropic API rate limits. If rate limiting becomes an issue, a semaphore can be added to ZoneManager without architectural changes. Starting with the higher limit ensures the fastest possible preloading.

### Appendix E: Memory Keep Radius

**Decision**: Keep zones within Manhattan distance ≤ 2 from the active zone (max 13 zones).

**Rationale**: Distance 1 (5 zones) is the minimum for smooth transitions — the player needs the active zone and its immediate neighbors. Distance 2 (13 zones) gives a buffer: when the player transitions, their old zone's neighbors are still loaded, making backtracking instant. At ~330 KB per zone, 13 zones use ~4.3 MB — negligible compared to the 100 MB budget. The extra memory is worth the improved experience.
